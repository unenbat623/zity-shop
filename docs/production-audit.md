## 🔴 P0 — Production-д гаргахаас өмнө ЗААВАЛ

### 1. Төлбөр нь симуляц мөртлөө захиалгыг "төлөгдсөн" гэж бүртгэдэг
`PaymentModal` нь 1.2 секунд хүлээгээд амжилттай гэж хариулна
([PaymentModal.tsx:63-71](../src/components/PaymentModal.tsx#L63-L71)). Дараа нь
`createOrder` нь `paymentStatus: 'paid'` тавьдаг
([useOrderStore.ts:113](../src/store/useOrderStore.ts#L113)).

**Үр дагавар:** production дээр хэрэглэгч мөнгө төлөлгүйгээр "төлсөн" захиалга үүсгэнэ.

**Засвар:** `VITE_DEMO_MODE` тугаар хаана. Production дээр демо унтарсан үед онлайн
төлбөрийн сонголтууд идэвхгүй болж, "төлбөрийн систем холбогдоогүй" гэж илэн далангүй
харуулна. Бэлнээр (COD) ажиллана. **Бодит QPay/SocialPay интеграц backend талд шаардлагатай.**

### 2. Захиалгын явц зохиомлоор урагшилдаг
`PROGRESS_TIMELINE` нь 30 сек → бэлтгэл, 2 мин → хүргэлт, 7 мин → хүргэгдсэн
([useOrderStore.ts:26-30](../src/store/useOrderStore.ts#L26-L30)). Хүргэгдсэн үед
COD захиалга автоматаар "төлөгдсөн" болно.

**Үр дагавар:** бодит хүргэлт хийгдээгүй байхад захиалга хаагдаж, орлого худал бүртгэгдэнэ.

**Засвар:** мөн `VITE_DEMO_MODE`-д хамааруулна. Production дээр төлвийг зөвхөн
Chef DB-ээс (`syncFromChef`) авна.

### 3. Odoo синк амжилтгүй байхад "амжилттай" гэж харуулдаг
`pushOrderToOdoo` нь bridge олдоогүй үед `SIM-SO-...` гэсэн хуурамч reference үүсгээд
`success: true` буцаана ([odooService.ts:172-184](../src/services/odooService.ts#L172-L184)).

**Үр дагавар:** ERP дээр захиалга байхгүй мөртлөө UI дээр ногоон "Амжилттай" харагдана.
"Дахин илгээх" товч ч үргэлж амжилттай гэж хариулна.

**Засвар:** демо унтарсан үед `success: false` + `simulated: true` тэмдэглэж, UI дээр
"ERP холбогдоогүй" гэж тодоор харуулна.

### 4. Нууц үг сэргээх урсгал дуусдаггүй
`sendPasswordReset` имэйл илгээнэ, хэрэглэгч холбоос дээр дарж `/login` руу буцна.
Supabase нь recovery session үүсгэнэ — гэхдээ **шинэ нууц үг оруулах форм байхгүй**.
Хэрэглэгч зүгээр нэвтэрчихээд нууц үгээ солихгүй.

**Засвар:** `onAuthStateChange`-ийн `PASSWORD_RECOVERY` эвентийг барьж, `/login` дээр
"Шинэ нууц үг тавих" форм харуулна.

### 5. Session-ы өөрчлөлтийг сонсдоггүй
`SupabaseAuthService.onAuthStateChange` бичигдсэн хэрнээ **хаана ч дуудагдаагүй**
([supabaseAuthService.ts:372](../src/services/supabaseAuthService.ts#L372)).

**Үр дагавар:**
- Refresh token хүчингүй болоход апп хэрэглэгчийг нэвтэрсэн гэж харуулсаар байна → бүх
  API дуудлага 401 өгч, дэлгэц хоосон болно (шалтгаан нь ойлгомжгүй).
- Өөр таб дээр эсвэл Zity Chef дээр гарахад энэ апп мэдэхгүй.

**Засвар:** store-д listener бүртгэж, session алдагдахад автоматаар зочин төлөвт
шилжүүлж мэдэгдэнэ.

### 6. Сагс хуучин үнэ, хуучин нөөцөөр тооцоолдог
`CartItem` нь `Product`-ийн бүтэн хуулбарыг localStorage-д хадгална
([useCartStore.ts:311-319](../src/store/useCartStore.ts#L311-L319)). Каталог дээр үнэ
өөрчлөгдсөн ч сагсанд хуучин үнэ үлдэнэ; `getCheckoutIssue` нь мөн хадгалсан `stock`-той
харьцуулна.

**Үр дагавар:** 3 хоногийн өмнөх үнээр захиалга үүсэх, нөөцгүй бараа захиалагдах.

**Засвар:** каталог ачаалагдах бүрт сагсыг дахин тааруулна (`reconcileWithCatalog`) —
үнэ өөрчлөгдсөн бол хэрэглэгчид мэдэгдэнэ, каталогоос хасагдсан бараа тэмдэглэгдэнэ.

### 7. Захиалгын дугаар 28 минут тутам давхцаж болно
`createOrderId` нь `Date.now().toString(36).slice(-4)` ашиглана
([useOrderStore.ts:71-78](../src/store/useOrderStore.ts#L71-L78)). 4 тэмдэгт base36 =
36⁴ ≈ 1.68 сая мс ≈ **28 минут тутам ижил утга давтагдана**.

**Засвар:** цагийн тамга + санамсаргүй суффикс.

### 8. Admin эрх нь "нээлттэй" талдаа унадаг (fail-open)
`isAdminEmail` нь `VITE_ADMIN_EMAILS` тохируулаагүй үед **`true`** буцаана
([env.ts:117](../src/lib/env.ts#L117)) — өөрөөр хэлбэл нэвтэрсэн дурын хүн
`/odoo-admin` руу орно.

**Засвар:** production дээр fail-closed. Зөвхөн dev дээр л нээлттэй үлдээнэ.

> ⚠️ Тэмдэглэл: `VITE_ADMIN_EMAILS` нь bundle-д ил орно. Энэ нь зөвхөн **UI-г нуух**
> хамгаалалт. Бодит хамгаалалт нь Chef backend-ийн `CHEF_ADMIN_EMAILS` + Supabase RLS
> дээр байх ёстой — тэр нь одоо байгаа тул өгөгдөл алдагдахгүй, гэхдээ UI-г нуух ёстой.

### 9. Хуваалцсан төхөөрөмж дээр өмнөх хэрэглэгчийн захиалга үлддэг
`zity-orders` нь localStorage-д **бүх** хэрэглэгчийн захиалгыг хаяг, утас, барааны
жагсаалттай нь хадгална. Дэлгэц дээр `userId`-аар шүүдэг ч өгөгдөл нь төхөөрөмж дээр
үлдэнэ, admin dashboard нь бүгдийг нь шүүлтгүй харуулна
([OdooAdminScreen.tsx:556-582](../src/screens/OdooAdminScreen.tsx#L556-L582)).

**Засвар:** гарахад тухайн хэрэглэгчийн захиалгыг цэвэрлэнэ; түүхийг 50-аар хязгаарлана
(localStorage quota); admin дэлгэц зөвхөн одоогийн хэрэглэгчийн локал захиалгыг
"локал" гэж тэмдэглэж харуулна.

### 10. Алдааны хамгаалалт (Error Boundary) байхгүй
Аль нэг дэлгэц render хийхэд алдаа гарвал **бүх апп цагаан дэлгэц** болно.

**Засвар:** `ErrorBoundary` нэмж, "Дахин ачаалах" товчтой ойлгомжтой дэлгэц харуулна.

## ⏭ Дараагийн алхам (энэ repo-гоос гадуур)

Эдгээр нь **backend/гуравдагч талын** ажил тул frontend дээр засах боломжгүй:

1. **Бодит төлбөрийн интеграц** — QPay / SocialPay merchant бүртгэл, backend дээр
   invoice үүсгэх + webhook-оор баталгаажуулах. Үүнгүйгээр онлайн төлбөр ажиллахгүй.
2. **Нийт дүнг сервер талд дахин тооцох** — купон, хүргэлтийн төлбөр, нөөцийг
   backend дээр шалгаж баталгаажуулах (одоо client-ийн илгээсэн дүнг итгэж авдаг).
3. **Захиалгын төлвийн жинхэнэ эх сурвалж** — Chef DB дээр `packing`/`shipping` төлөв
   болон operator панел.
4. **Zity Points-ыг DB рүү зөөх.**
5. **Захиалга цуцлах API** — одоо Chef дээр үүссэн захиалгыг Delguur-ээс цуцлах
   боломжгүй.
6. **Алдаа хянах систем** (Sentry) + uptime monitoring.
7. **Хууль эрх зүйн баримтыг бөглөх** — `/terms`, `/privacy` хуудсууд нэмэгдсэн.
   Гэхдээ [`src/constants/legal.ts`](../src/constants/legal.ts) доторх компанийн нэр,
   **улсын бүртгэлийн дугаар, хаяг, утас** нь одоогоор орлуулга (`—`) байна.
   Deploy хийхээс өмнө бодит мэдээллээр солино. Мөн буцаалт, хариуцлагын хязгаарын
   заалтуудыг **хуульчаар хянуулах** шаардлагатай — эдгээр нь загвар текст.
